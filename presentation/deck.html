01 — Where this comes from

System security assessment

Broad system assessment used to be a niche tool.

Then: build a lab

For when failure isn’t tolerable

  • Stand up a lab around one product or platform
  • Full breadth, plus deep focus where defects are security critical
  • One big, expensive, point-in-time verdict

Now: make it repeatable

For every system you build

  • Same breadth, same rigor, same method
  • Light checks on every change, full runs when it matters
  • Largely automated with AI. Humans keep the judgment calls.

The method works. It just never scaled past the lab. That’s what we’re going to fix.

02 — What this isn’t

System security assessment

It isn’t a pentest.

The pentester hears

“Break into the system.”

The system owner hears

“Tell me how secure my system is.”

A pentest finds point-in-time vulnerabilities. Useful! But it doesn’t tell you how secure the system is, and it’s stale by the next deploy.

02 — What this isn’t

System security assessment

AI code review: necessary, not sufficient.

Keep it in the pipeline

  • Modern LLMs are really good at finding code defects
  • Runs on every PR, at the speed code ships
  • Keeps up with AI-written code
  • Way past what old static analysis could do

What it can’t see

  • Design flaws: a broken protocol, perfectly coded
  • How components behave together
  • Deployment, config, and operations
  • Whether the requirements are even right

It’s one stage of the program, not the program.

03 — History · Before computers

System security assessment

We’ve been poking at security for a long time.

1851

Alfred Hobbs picks the “unpickable” locks

Opens the Bramah and Chubb locks at the Great Exhibition, then argues that talking openly about weaknesses helps honest people more than crooks.

1883

Kerckhoffs writes down the rule

A system should stay secure even if the enemy knows everything about it except the key. Design gets judged in the open.

03 — History · Early computing

System security assessment

Then the computers showed up.

1970

Ware Report

Computer security is a whole-system problem: hardware, software, people, procedures.

1972

Anderson Report

Air Force planning study. Gives us the reference monitor and makes the case for penetration testing.

1974

Karger & Schell

Tiger team on Multics. Finds design and code holes, and sketches the trojaned compiler a decade before Thompson.

03 — History · What changed

System security assessment

Then the systems got too big to get your arms around.

Then

Self-contained, self-hosted

  • Your hardware, your data center, a few vendors
  • Changed in releases, months or years apart
  • A small team could read the whole design

Now

Cloud and third parties

  • Cloud platforms, SaaS, and third-party APIs
  • Much of the risk lives with third parties
  • Changes constantly, much of it written by AI

Assessment cost grew with complexity: more time, more effort, more expertise. So broad assessment retreated to the niche cases, the lab and the system that couldn’t fail.

03 — Where that left us

Real system assessments became rare.

So did the people who can do them. AI changes that math.

04 — Philosophy · What security is

System security assessment

Security is an emergent property.

Ideation

Design

Build

Deploy

Operate

It emerges at every stage

Every decision adds or removes some: a design trade, a library pick, a deploy flag, an ops shortcut.

It gets bolted on at every stage

You can’t assess one stage and call it done. Assess the whole system.

04 — Philosophy · Trade-offs

System security assessment

The -ilities fight each other.

Security vs. performance

Encrypt and inspect everything, and you pay for it in latency.

Security vs. availability

The auth service is down. Fail closed and lock everyone out, or fail open?

Security vs. usability

Add friction and users build workarounds you never assessed.

Security vs. maintainability

Controls nobody understands get misconfigured, then switched off.

Assess security alone and you miss the trade the team made to hit its latency target. Assess it in context.

04 — Philosophy · What we’re assessing

System security assessment

Security you can see, and security you can’t.

Functional · You can see it

  • Passwords and authentication
  • Encryption
  • Roles and entitlements
  • Access control

Non-functional · You can’t

  • No race conditions
  • No side-channel leaks
  • No exploitable code defects
  • Resilient in the face of poor configuration
  • Holds up under abuse

A system assessment has to cover both. Breadth-first attackers live in the right one.

05 — The shift

AI does the work. Humans own the judgment.

We’re at the point where AI can help drive broad assessment in a repeatable, scalable way. What follows is the process I’ve used to build assessment labs, reworked to run with AI inside the development process.

Four human gates: the requirements, the test plan, the tests, and the verdict.

Stage 01 / 07 — Ingest

System security assessment

01

Start with a description of the system.

AI does

Reads design docs, diagrams, API specs, IaC, and code

Builds the model: components, data flows, trust boundaries, identities

Lists the third parties we trust, and for what

Flags gaps: “the docs say X, the code says Y”

Human · light touch

Hand over the real description, not the brochure

Spot-check the model against reality. Everything downstream depends on it.

Output → a system model, versioned in the repo next to the code

Stage 05 / 07 — Run in CI/CD

System security assessment

05

Run it in the pipeline, at the right cadence.

Per PR · light

AI code review plus tests touching the changed areas

Material change

Full run. If the design moved, rerun 01–03 too.

On a schedule

Full run, daily or weekly, with the agent sweep.

Not every build

Full runs are heavyweight. Spend them where they count.

Human · nothing routine

Failures route to the owning team, like any broken build.

Output → fresh results when it matters, not once a year

06 — In practice · Trust, but verify the robot

System security assessment

Where this will burn you, and why the gates exist.

Made-up architecture

The model looks right and isn’t. Check it against reality.

Tests that test nothing

Green forever. Plant the bug and prove they fail.

AI sprawl

AI tools want to be helpful, so they keep generating findings, tests, and agents. Prune and cap.

Drifting results

Version the prompts and models, so a diff means the system changed.

A map for attackers

The system model is sensitive. Protect it wherever it’s processed.

Rubber stamps

A gate nobody reads is no gate. Humans actually sign.
